# Code review, November 2026

A review of the whole app for structure: implicit state machines, god objects, functions that do
everything, code that should live in its own module, and duplicated UI. Each finding has a fix; the
fixes are committed in the order below. Performance is reviewed last, in its own section.

## Backend

| # | Finding | Fix |
|---|---|---|
| B1 | `src-tauri/src/lib.rs` is 1,200 lines: about 120 commands of every area in one file, and `run`'s setup (230 lines) mixes resolving folders, the Folio migration, smoke overrides and logging. | Commands move to `src-tauri/src/commands/`, one module per area. `run` keeps the builder; setup steps become named functions. The contract reads every command module. |
| B2 | `Core::start` is 200 lines that build twenty components and spawn a dozen background tasks, with `if background` repeated five times. `core.rs` has empty section markers left from the component refactor. `Core::play` decides recording or speech inline. | `Core::start` = `build` (components) + `spawn_tasks` (background work). The choice of what narrates a book becomes one function. Empty markers go. |
| B3 | `aoide-library`'s `Library` keeps books, progress, the audio cache, bookmarks, listening, details, collections, discovered files, lookups and stored values in one 1,200-line `lib.rs`. Migrations are one 270-line function whose latest version is a literal (`0..=12`) that must be changed by hand beside each new step. | One module per table group, as articles, feeds, recordings and sites already are. Migrations become a list of steps; the latest version is its length. |
| B4 | `core/recordings.rs` is 1,600 lines: stored rows, live state, decoding, the sync queue, the quick check, transcription, matching, storing, model downloads and layout. `transcribe_block` (190 lines) runs the quick check *and* a block, gated by `done == 0 && !checked`. | `core/recordings/` with `live.rs` (live state, queue, decoding), `steps.rs` (check, `quick_check`, `next_block`, matching), `attach.rs`, `speech_models.rs` (choice and downloads) and `layout.rs`. |
| B5 | Long single functions: `Playback::state` (110 lines, three return shapes inline), `encode_m4b` (160), `search_blocking` (130), `scan_blocking` (110). | Split each into named steps; `Playback::state` gets one function per session kind. |
| B6 | The browser driver keeps `Option<(Browser, bool)>`, the `bool` meaning "has a window", and every caller `expect`s the option. `Library.conn` carries a stale `allow(dead_code)`. | A named `Running { browser, visible }`; the driver hands out a guard mapped to the browser, so callers cannot reach a missing one. The allowance goes. |

## Interface

| # | Finding | Fix |
|---|---|---|
| U1 | 727 relative imports (`../../api`). | `@/` alias for `src/` in Vite, Vitest and TypeScript; every import uses it. |
| U2 | About forty components restyle `<button>` from scratch (`.signin__button`, `.pair__button--primary`, `.confirm__button--danger`, …) with the same height, radius and fills. | `UiButton` (variants `plain`, `primary`, `accent`, `danger`, `quiet`; sizes) used everywhere a pill button is drawn. |
| U3 | Cards are restyled per screen (`.storage__card`, `.item-page__card`, `.find__card`, `.feeds__card`, …): the same page fill, radius, padding and shadow. | `UiCard`. |
| U4 | Spacing, radii and control sizes are literals (`gap: 8px` 75 times, `10px` 48, `6px` 43; radii 10/14/16/22). | Spacing, radius and size tokens in `theme.css`; a style test keeps literals out of components. |
| U5 | Implicit state in stores: `stores/audiobooks.ts` keeps `scanning`, `pairing` and `adding` as three flags, and `stores/discovery.ts` keeps `scanning`, `fetching` and `importing` apart, for one activity that is never two at once. | One `activity` value per store (a union carrying its progress), changed only by `run`, which also refuses a second activity while one is under way; the old names are read from it. |
| U6 | The "one of a few" toggle (Page or Lines, Light or Dark, a range of days, a kind of item) is built four times, each with its own track and chosen style. | `UiSegmented`, a labelled group of toggle buttons. |
| U7 | Find books and Find audiobooks each carry the same folder form (three one-per-line boxes, a switch, a save button and its "Saved." note, with its own `lines()` helper and form state) and the same row of filter tabs with counts, with 28 identical style rules between them. | `ScanFolders` (`components/find/`) owns the form and its state, given the stored folders and a `save`; the tabs are `UiSegmented`, whose options now carry an optional count (the library's kinds use it too). |
| U8 | `ItemView` (966 lines) keeps the Contents card's own state (each chapter's audio, a refresh timer, a chapter state per row, preparing one chapter) beside the page's, and copies the extraction-notes link and list into two cards. Its small buttons are still drawn by hand. | `BookContents` owns the chapter list and its audio state; `ExtractionNotes` the notes; the small buttons are `UiButton`. |

## Performance

Reviewed after the structural fixes. Timings are from this machine (NVMe, btrfs); each row was
measured before and after its fix.

| # | Finding | Fix |
|---|---|---|
| P1 | The library database uses SQLite's default rollback journal with `synchronous = FULL`: every commit is an fsync, about 3.6 ms on this disk. Saving a place, a minute of listening or a feed entry each holds the one library lock for that long, and a scan that finds 500 new EPUBs stores them one commit at a time (1.8 s under the lock). | The database writes ahead to a log (`journal_mode = WAL`, `synchronous = NORMAL`): 500 single commits take 44 ms. A scan's files are stored in one transaction with one prepared statement: 2.4 ms. |
| P2 | Idle, Aoide woke about 166 times a second. Most were the media keys: `souvlaki`'s MPRIS thread waits for news with a 10 ms timeout, forever (both of its Linux back ends do). | On Linux, Aoide serves MPRIS itself with zbus (already built for the opener plugin): zbus waits on the bus socket, and what plays is sent as `PropertiesChanged` signals when it changes. `souvlaki` stays for macOS and Windows. Idle wakeups: 166 → 69 a second. |
| P3 | The tick loop looks at the player every 33 ms whether anything plays or not: it builds the player's state, locks playback, the output, the sleep timer and listening, and compares the state with the last one sent. | Playback tells of each change (a session started or stopped, play, pause, a seek, speed, volume, a failure; the sleep timer too). The loop ticks every 33 ms while something plays, a sleep timer runs, or for two seconds after a change, and otherwise waits for the next change, looking anyway once a second. Idle wakeups: 69 → 29 a second; CPU over ten idle seconds: 20 → 8 ticks. The engine's health check (one loopback request every 3 s) stays: it keeps the engine's status live. |
| P4 | Listing the library (on start and after every change) runs six to eight queries per item, each taking the library lock: its settings twice, its place and how far in, its audio bytes, its preparation, its recording. Audio bytes are summed by reading every segment row of the book, word times and all. 1,000 items with 90,000 segments: 41 ms per listing with SQLite optimised, 110 ms in a debug build. | Listing reads each table once, under one lock (`Library::all_progress`, `Library::book_values`, `audio_usage`, `recordings`), and passes the settings it read to the host instead of the host reading them again. Schema v13 adds a covering index `segments(book_id, bytes, created_at)`, so audio per book is summed from the index: 45 → 7.7 ms for those 90,000 segments. Listing: 41 → 17 ms. |
| P5 | Each refresh of the library replaces every summary and the list of collections, though most did not change; every card is drawn again, and each card's menu is rebuilt (it lists the collections). With 400 cards, a refresh that changed nothing took 110–130 ms in the test DOM. | The library store keeps each summary that did not change (and the collections, and the list itself when nothing changed), so only changed cards are drawn again: 3 ms when nothing changed. |
| P6 | The reader's page is one component, `ChapterText`, whose every word reads the word being spoken; each new word (several a second while listening) draws the whole chapter again. A 6,000-word chapter: 26.8 ms a word in the test DOM. | `ChapterSegment` draws one sentence and is given whether it is spoken and which word, so a new word draws the spoken sentence again and nothing else: 4.1 ms a word. Its classes are its own (`chapter-segment…`); following the spoken sentence and finding the reading place select them. |
| P7 | The aligner's loop wakes every 150 ms for as long as Aoide runs, with or without an aligner set up, to see whether anything waits. | It waits until work is queued (or, when the aligner was offline, until the retry is due), then keeps its 150 ms pause between requests. Idle wakeups: 29 → 19 a second; CPU over ten idle seconds: 8 → 4 ticks. What is left is mostly the window's own main loop. |
